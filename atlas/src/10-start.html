What PrecisePK is

PrecisePK is clinical dosing software. A pharmacist enters a patient, a drug, the doses given and the blood levels measured. The software estimates that patient's own pharmacokinetics and recommends a regimen that reaches a target such as an AUC or a trough.

Three ideas carry most of the codebase:

  • Population model. A published study (for example Rodvold 1988 for vancomycin) predicts a typical patient's clearance and volume from covariates such as creatinine clearance and weight. This prediction is the prior.
  • Bayesian fit. When measured levels exist, the engine moves the parameters away from the prior until predicted levels match measured ones, weighing both. The result is the posterior (the individual estimate).
  • Target search. With prior or posterior parameters in hand, the engine simulates candidate regimens and picks the dose, interval and infusion time that hit the target.

All of that maths lives in one C++ library, PK-Library. Everything else stores cases, signs people in, connects to hospital EHRs, draws the charts, or reports on populations.

Lives outside these repositories

ECS task and service definitions, IAM policies, the production MySQL schema (DDL), Amplify console settings, and Datadog configuration.

One request, end to end

A dose recommendation is the most typical request. It shows the middleware every Node service shares and where the engine is called. from PreciseRx-Main/src/controllers/index.js:54-89 and prediction/dose/post-output.js:28-43; the handler lines are

sequenceDiagram
  participant B as Browser
  participant G as Gateway
  participant M as Main
  participant V as Valkey
  participant P as PK-Library
  B->>G: POST /main/v1/prediction/dose/output with cookies
  G->>M: POST /prediction/dose/output
  M->>M: helmet, CORS, cookie parse, compression
  M->>M: verify access and id tokens against 6 pools
  M->>M: both tokens must name the same user
  M->>V: is revoked:user:sub set? (30 s local cache)
  M->>M: role check: admin or user
  M->>M: Joi validation, errors logged but not enforced
  M->>P: dosage_regimen(patient, drug, settings, pk, target)
  P-->>M: regimen, or an empty object if the engine threw
  M-->>B: 200 with the JSON result

The request body carries the whole clinical picture every time: patient, drug, settings, prior and posterior PK parameters, and the target. Main keeps no state between calls.

Suggested reading order

  1. How the stack runs locally: the umbrella Makefile, docker-compose.yml and src/services/nginx/conf.d/. See Local development.
  2. The frontend's HTTP layer, src/actions/AxiosRequestWrappers/, to learn how every call is made. See Frontend platform.
  3. Main's src/controllers/index.js (the middleware order) and one route end to end, such as prediction/dose/post-output.js.
  4. PK-Library in this order: src/drug/vancomycin.hpp (model choice), study/vancomycin/vancomycinrodvold1988.hpp, vancomycintdms.hpp, model/model.hpp, bayesianfitting/bayesianfitting.cpp. See the worked example.
  5. The binding's fit_and_plot in bindings/nodejs/pklibraryjs.cpp (about line 1668), which connects JavaScript to the maths.
  6. Database's app/__init__.py and app/middlewares/before_requests.py, then app/models/hospital/case.py.
  7. Databridge's Epic launch: controllers/ehr/epic/get-launch.js then get-callback.js.
  8. Shared-JS src/middleware/CognitoAuth.ts and TokenPairing.ts, which every Node service uses to authenticate.
