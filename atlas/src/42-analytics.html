PreciseRx-Analytics

Analytics turns stored cases into institution-level reports. It is not on the live dosing path. Its most involved feature, Model Analytics, is a back-test. For historical cases it re-predicts a measured level from the levels before it, once with the population prior and once with the fitted posterior, so accuracy can be compared.

What actually happens at the last step

getGraphHashList awaits SMEMBERS but never returns the result (src/utils/redis-utils.js:128-130). The completion handler always sees undefined and takes its fallback. The fallback emits serum:failed_job {level} to the whole /serum-analysis namespace, and returns before setting the 24-hour TTL (controllers/serum-analysis/on-completed-serum-job.js:57-65). The Redis adapter relays it to every server instance, so every connected Model Analytics user, in every institution, receives every finished job, labelled as a failure. Each level carries the case number, serum-level ID, drug model, observed concentration and predictions, but no names (PreciseRx-Database/…/get_serumpredictions.py:71-80).

Fixing only the missing return is not enough. serum:calculate joins whatever graphHash the client sends (calculate.js:236). The hash is also predictable, because filters (an object) is interpolated into a string as [object Object] (hash-utils.js:53). A safer design derives the room from the verified user.

HTTP auth. Every HTTP route except /HealthCheck runs the standard chain: both tokens, pairing, revocation, then admin-or-user. A limit of 120 requests per minute per IP covers everything.

Socket auth. Sockets are checked only at the handshake: both tokens, pairing and revocation, but no role. After that the connection keeps working when the token expires or the user is revoked, and there is no payload validation or rate limit.

The worker

  • Entry and threads. The entry point is src/workers/predict-serum-level/src/index.js. It runs a workerpool of worker.js threads, one fewer than the CPU count by default.
  • How it runs. It has no HTTP listener and no health signal. It polls SQS only when a priority_analytics message arrives.
  • Settings. It uses a hard-coded standardizedSettings object rather than the institution's settings (worker.js:11-43).
  • Outlier check. Any prediction ≤ 0.5 or ≥ 35 is rejected as an outlier, for every drug.
  • Error checks. With PK-Library 1.6.1, the checks for an empty fit result can't fire, because {} is truthy (worker.js:80, 105).
  • Unhandled rejections. The completion and failure publishers aren't awaited. A failed DeleteMessage becomes an unhandled rejection, which crashes Node 24 by default.
  • Redelivery. When the job hash is missing or its version has changed, the message is never deleted, so SQS redelivers it every 60 s.
  • Env vars. It needs every server env var at boot, because it shares env.js.

Tests and build

  • Jest 30 in test/, mirroring src/. There are no tests for the socket listeners, completion handlers, worker, redis-utils, SQS, or the therapeutic controllers. That is why the key bugs above went unnoticed.
  • hash-utils.test.js stubs uuid, which is ESM-only in version 13, so real key derivation is never exercised.
  • Four Jenkinsfiles build the server and worker images for production and staging. They run no tests and have no deploy step.
